# 源码组织评估与迁移方案

评估基线：`ad65218`。本次只评估组织方式，不迁移运行代码、不改部署入口或运行数据。

## 当前情况

`src/` 顶层有 17 个模块（不计空的 `__init__.py`），混合了应用入口、对话编排、模型访问、业务数据、网络与事务设施、管理控制台和运维命令。顶层数量适合通过分包减少；较大模块还需要按职责拆分，才能减少修改时相互影响。

以下为包含函数内部延迟导入在内的静态依赖检查，并不表示目前所有循环都会造成启动异常。

| 位置 | 现状 | 建议 |
| --- | --- | --- |
| `deepseek_client.py`（609 行） | 模型请求、技能授权、工具循环、熔断、历史、压缩和投递后提交共存 | 对话编排放应用层；SDK 与请求适配放模型层；历史管理独立 |
| `channels/core.py`（396 行） | 管理共享业务流程，包含本地命令、媒体、模型闸门、提示与投递 | 移到应用层，通道保留事件翻译和平台 API |
| `vision_utils.py`（698 行） | 下载、视觉请求、缓存退避、标签处理、采集触发和生图共存 | 按下载、识图、生图和采集职责分离 |
| `vision_utils.py` 与 `stickers_utils.py` | 识图完成后调用表情包采集，表情包模块又导入视觉模块的下载函数 | 下载下沉，采集由上层协调，表情包仓库只处理图片数据与索引 |
| `runtime.py` | 通用轮次事务中的 `reset_context()` 直接访问 `deepseek_client._conversations` 与触发器 | 轮次设施仅管理有效期与事务；会话重置由应用层协调 |
| `channels/__init__.py` | 导出契约时同时导入 `core`，读取通道契约也会加载模型相关代码 | 契约独立；包初始化保持轻量 |
| `tools/__init__.py`（363 行） | 包含上下文类型、Provider 基类、注册表、全量 Provider 初始化与公共函数 | 分为契约、注册表和显式初始化，避免包导入时创建整套工具 |
| `admin.py`（367 行） | 自然语言解析、身份判断、配置、日志、进程调度在同一文件 | 管理包内按解析、路由和操作服务拆分，保留执行前权限校验 |
| 数据路径 | 配置、画像、跑团、表情包、管理任务等分别按 `__file__` 层级计算项目目录 | 集中定义项目根目录与数据路径，文件搬迁不改变数据位置 |
| 管理配置项清单 | `admin.config_keys()` 解析 `src/config.py` 源码中的 `os.getenv` | 配置模块显式提供可查看项、可修改项及只读项，不依赖源码路径与语法形式 |

## 建议的目标目录

## 依赖边界

- `main.py` 负责组装与初始化；`runner.py` 负责启动包装，不放业务规则。
- 通道将原始事件转换为契约对象，调用管理路由或普通消息流程；普通业务不导入具体通道实现。
- 应用层协调触发、历史、模型和工具，负责进度提示的阶段语义。
- Provider 是工具适配入口，调用媒体或业务状态服务；业务状态模块不反向调用 Provider 或模型编排。
- 识图返回描述与标签；采集协调器将图片下载结果交给表情包仓库。两者通过上层组合。
- 基础设施不导入会话历史、触发策略或其他业务模块；轮次提交后需要的业务动作由上层提供。
- 管理权限不进入模型工具列表。管理路由和操作服务保留两次身份检查，`ADMIN_QQ` 继续是私聊只读配置。
- `__init__.py` 只保留轻量导出，避免隐式创建 SDK 客户端、注册全部工具或导入官方通道补丁。

## 迁移顺序

### 第一阶段：建立迁移前提

1. 集中定义项目和数据路径，替换分散的 `parent.parent`、`dirname` 计算。
2. 配置模块显式导出配置项描述，管理入口不再解析源码 AST。
3. 拆出工具契约与注册表；先保证行为与现有权限快照一致，再把注册移至启动组装。
4. 将会话重置从轮次设施中移出；解除视觉与表情包的下载、采集双向依赖。

这一阶段重点减少隐式依赖，顶层文件数量暂时不会明显下降。

### 第二阶段：按包迁移

1. 迁移基础设施、业务状态和媒体模块，逐包更新导入与测试。
2. 迁移管理模块以及独立控制 worker。
3. 迁移消息流程、契约和普通命令，保留两条通道已有发送行为。
4. 迁移离线运维命令。

每个提交只迁移一个职责组，先不同时修改工具行为、超时策略或数据格式。内部旧导入统一更新；只对外部启动入口保留薄包装，避免在顶层留下大量转发文件，也不通过 `sys.modules` 别名掩盖迁移。

### 第三阶段：拆分对话编排

将 `deepseek_client.py` 中的模型传输、历史与压缩、技能工具循环逐步拆开。保持现有公开能力与回归结果，再按实际改动需求进一步拆分跑团、视觉等大模块。

## 兼容与验收

- 保留 `python -m src.runner` 和 `python -m src.main`，避免改坏 `start.sh` 的启动和进程识别。
- 保留旧的 `python -m src.log_report`、`python -m src.migrate_data` 为薄命令入口，内部转调新 CLI。
- 管理 worker 的模块路径、脱离 screen 的方式、继承环境清理和固定 argv 必须一起更新验证。
- 数据目录、存档身份编码、表情包文件名与索引格式均不变；本次组织调整不迁移真实数据。
- 测试应导入实际模块并在实际调用位置 patch，避免补丁仍作用于旧的转发模块导致测试失真。
- 必跑管理员、权限快照、会话隔离、取消后禁止晚写、模型与工具提示、分条投递、表情包、代理下载和日志链路检查。
- 增加导入边界检查：契约不加载 SDK；基础设施不导入应用；读取技能目录仍不加载全部正文；官方 SDK 补丁仅在启用通道时加载。
- 目录迁移完成后，服务器先做导入与配置检查，再 reload，并核实 Python、OneBot 和官方通道状态。

建议从第一阶段开始，按包逐次迁移。最终顶层仅保留稳定入口与配置，完整迁移需要多组回归，属于中等规模重构。
